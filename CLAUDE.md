# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Laravel 12 / PHP 8.2+ multi-unit CMS (first deployment: Nam Bình Dương university), built with `nwidart/laravel-modules`. Two active modules: `CmsBackend` (admin + shared services) and `CmsFrontend` (public site). Module names are deliberately neutral — never name modules/controllers after a customer. `README.md` (Vietnamese) is the authoritative design/decision log; read it before architectural changes. The directory is a git repository (branch `main`, remote `origin` = github.com/levantrieu19081995/cms-multi-theme, **public**: never commit `.env`, DB backups, deploy archives or `storage/` contents; `.gitignore` already blocks them).

## Commands

```bat
npm run dev:all        # Laravel server + Vite together, ALL themes (scripts/dev-all.ps1); website http://127.0.0.1:8011/, admin http://127.0.0.1:8011/cms, login at /cms/login
php artisan serve --host=127.0.0.1 --port=8011   # or run separately...
npm run dev            # ...Vite dev server ONLY (no Laravel). For PHP + Vite use dev:all / dev:all-themes / dev:<theme>
npm run build          # production Vite build (all enabled modules in modules_statuses.json)
npm run build:cms      # build only CmsBackend + CmsFrontend, all themes (CMS_BUILD_PROJECT profile, scripts/project-profiles.mjs) -> build-exports/cms/build
npm run build:khung    # `khung` profile in scripts/project-profiles.mjs: no modules listed (bare framework)
npm run dev:all-themes # Laravel + Vite, every public theme (same as dev:all)
npm run dev:default | dev:nbd | dev:bda | dev:bdav2         # Laravel + Vite, ONE theme (also: npm run dev:theme -- nam-binh-duong)
npm run start:kn       # Khuyến nông local: Laravel + Vite, single mode, theme default (project khuyen-nong)
npm run build:all-themes                           # every theme -> build-exports/all-themes/build (same set as build:cms)
npm run build:default | build:nbd | build:bda | build:bdav2   # ONE theme -> build-exports/themes/<theme>/build (also: npm run build:theme -- ban-de-an)
node scripts/theme-build.mjs <all|theme> --check-only   # registry + Blade @vite() check, no Vite build
php artisan test                                  # PHPUnit (Unit + Feature suites)
php artisan test tests/Feature/SbutThemeTest.php  # single file
php artisan test --filter=methodName              # single test
vendor/bin/pint                                   # PHP formatting
php artisan optimize:clear                        # after moving the source or changing config
```

- Tests hit the real configured DB (`cms_workspace`; sqlite lines in `phpunit.xml` are commented out). Existing HTTP tests wrap changes in transactions that roll back — keep that pattern. Do not run migrations/seeders or alter the DB just to boot the app.
- `public/storage` must symlink into *this* source (`php artisan storage:unlink && storage:link` after relocating).
- Vite scans `resources/assets/{js,css,sass}/**` recursively plus each module's `vite.config.js`. **CmsFrontend entries no longer come from a blind glob**: they come from the registry `scripts/theme-profiles.mjs` (see "Dev/Build per theme"). A new theme's CSS/JS must be registered there (and needs a rebuild, `@vite` in the screen/component).

## Architecture: screens/themes

Request flow: `Route → shared Controller → Service (data + business rules) → ScreenTheme resolves theme → Screen view → layout/components`. Views never query the DB or decide permissions; data is prepared in controllers/services (e.g. `Modules/CmsFrontend/app/Services/HomePresentation.php` builds and caches homepage blocks, keyed by theme/db/locale).

- Only the **public** site is themable; admin is hard-wired to `screens/default` (do not add admin themes). Four themes (checked 2026-11-17): `default` (Khuyến nông, project `khuyen-nong`), `nam-binh-duong` (SBUT), `ban-de-an`, `bandean-v2`; the last three extend the shared layer `_campus`. Selection = option `cms_public_theme` (old `cms_home_theme` is ignored). `bandean-v2` is a **site of its own** in `projects.php` that works on the DATA of Ban Đề án (`'data_project' => 'ban-de-an'`): `ProjectContext::dataKey()` is used for posts/publication history/social accounts, while `key()` stays `bandean-v2` for theme, guides, login design and permission manifest; a project without `data_project` owns its data. Every project key needs a folder `Modules/CmsBackend/resources/guides/<key>/` (guard: `SocialGuidesTest`). Bump the theme `version` in `screens.php` whenever a renderer or config that affects the homepage fragment cache changes. The live layout plan is cached forever (`HomepageLayoutService::live`): after changing a theme layout class run `homepage:layout-install` / clear that cache, or the old renderer name fails with `Screen not found`. Rules that bite in `bandean-v2`: `css/screens/bandean-v2/palette.css` and `typography.css` are GENERATED by `node scripts/bandean-v2-derived-css.mjs` (`--check` reports drift; rerun after editing any `font-size`/blue colour, never hand-edit); scroll-linked effects must be compositor-only (`transform`, never `width`/layout per frame); no `backdrop-filter`/blur on big surfaces; main menu is `position: fixed` (`.is-pinned`), not sticky. Full design notes (banner, sections, carousels, palette, fonts): `docs/themes/BANDEAN-V2.md` — read it before touching that theme.
- Theme registry, legacy-view-name mapping, `shared_views`, per-theme `home_sections` (category slugs), `statistics`, `audience_links`, and cache `version`: `Modules/CmsBackend/config/screens.php`. Resolution/fallback: `Modules/CmsBackend/app/Services/ScreenTheme.php`; Laravel view-finder hook: `app/Support/ScreenViewFinder.php`. Unregistered/unknown DB key → falls back to `default`; missing theme views fall back to default screens.
- Views live at `Modules/<Module>/resources/views/screens/<theme>/{layout,home}.blade.php`, `components/`, `pages/`. Controllers call neutral view names (`cmsfrontend::screens.home`, `cmsbackend::screens.pages.news.index`) or `ScreenTheme::view(surface, screen)` — never hardcode a theme key in a controller. Theme assets: `resources/assets/{css,js}/screens/<key>/`.
- **Shared view layer** (`screens/_campus/`): views the campus themes (`nam-binh-duong`, `ban-de-an`) have in common live once there instead of as identical copies. Lookup order for a view = the theme's own folder, then the layer it declares (`'extends' => '_campus'` in `screens.php`; `ScreenTheme::lookup()`), then `default`; a layer is not a theme (underscore name, not selectable, never read by `default`). The theme's own file always wins, so a theme diverges by copying the file into its own folder. Homepage renderers use the same order (`HomepageBlockRegistry::rendererPath`) but still never borrow another theme's. Build side: `layers` in `scripts/theme-profiles.mjs`. Guard: `tests/Feature/ScreenThemeLayerTest.php` (also fails when a layer file still has a twin in a theme).
- Adding a theme: register key (lowercase/digits/hyphens) + label + `surfaces: public` in `screens.php`, create only the views that differ, test fallback/cache/permissions, bump the theme `version` when changing config that affects fragment cache. Theme must not change DB, permissions, menus, or workflow, and must not get its own controller/service just for layout.
- Theme content comes from existing posts/categories (no sample data seeded into the DB); empty blocks show an "updating" state.
- **Design standards** (`docs/design-standards/TIEU-CHUAN-THIET-KE.md`) apply to every theme and login design; follow them when building from a new design. Nested rounded boxes: `outer radius = inner radius + padding` (+ border width when the outer box has a border), written in CSS as `calc(var(--r-inner) + var(--pad))`, never as two independent hard-coded numbers. Theme colour palettes (variables, hex values, contrast ratios) are listed in `docs/design-standards/BO-MAU-THEME.md`; update it when a theme's colours change.
- **Homepage Layout Manager** (`Modules/CmsFrontend/app/Homepage/`): the public homepage of every theme is built from a layout of blocks (zones, variants, enabled, order) instead of a fixed `home-content` view. Block types = `Definitions/`, per-theme zones/renderers/default layout = `Themes/`, all listed once in `HomepageBlockRegistry`; layout and per-theme block settings live in `homepage_block_instances/theme_blocks/block_settings`; with nothing installed the code default layout is used. Developers arrange it in Developer Settings → "Bố cục trang chủ" (preview → apply); admins only edit block content sources in "Cài đặt trang chủ". Effects belong to the shared framework: blocks declare preset KEYS (`EffectCatalog`), the page loads only the `effects/auto/*` entries those presets need, and every build profile contains them. How to extend: `docs/homepage-layout-manager/HUONG-DAN-MO-RONG.md`.
- **Developer Settings → tab "Tài khoản"** (`Services/Developer/AccountAdmin.php`, `DeveloperAccountsController`, partial `accounts.blade.php`, lang `developer_accounts`): list of all accounts, password reset (signs the account out everywhere), lock/unlock, role assignment and role permissions (through `PermissionAvailability::syncRole`). Developer session only; every action is written to the activity log without the password.
- **Opt-in for the two transactional HTTP tests** (`ScreenThemeHttpTest`, `SbutThemeTest`; they only use `DB::beginTransaction()`/`rollBack()`): `ALLOW_DEV_DB_TRANSACTIONAL_TESTS=1 DB_DATABASE=cms_workspace CMS_DB_DATABASE=cms_workspace php artisan test tests/Feature/ScreenThemeHttpTest.php tests/Feature/SbutThemeTest.php` (17 pass, 2026-11-09). Without the flag `tests/TestCase.php` still refuses `cms_workspace`. Never set the flag for tests that use `RefreshDatabase`.
- **Login designs**: the look of the sign-in/register page is a "design" independent of the public theme; the controllers (`LoginController`, `RegisteredUserController`, `AuthPageContext`) stay shared and return `cmsfrontend::screens.pages.auth.login` (= `@include(LoginDesigns::view())`). A design is a folder `Modules/CmsFrontend/resources/views/auth/designs/<key>/` (`login.blade.php`, `auth.css`, `design.php`) found by scanning (`_template` skipped); `scripts/theme-profiles.mjs` adds every `designs/*/auth.css` to EVERY build. Choice = option `cms_login_designs` (`{project key: design key}`, Developer Settings → tab "Đăng nhập"); none = design named like the project's theme; unknown/not built/broken → theme design → `default`, never a 500. Brand (name, logo) comes from the theme, not the design. Service `Modules/CmsBackend/app/Services/LoginDesigns.php`; tests `tests/Feature/Login` (SQLite :memory:); how to add one: `docs/login-designs/HUONG-DAN-THEM-GIAO-DIEN.md`; the `bandean-v2` design and details: `docs/CHI-TIET-KIEN-TRUC.md`.
- **Career orientation (RIASEC)** is a feature cluster of its own on the survey engine: survey type `career`, admin `/cms/dinh-huong-nghe-nghiep` (`cms.nghe-nghiep.*`), public `/dinh-huong-nghe-nghiep` (`cms.frontend.nghenghiep.*`), permissions `nghenghiep-*` (must be enabled in Developer Settings → Permissions on a deployment with a permission manifest), own Feature Registry switch `career`. Survey and career clusters are registered from one declaration (`$surveyCluster` in `Modules/CmsBackend/routes/web.php`, loop in `Modules/CmsFrontend/routes/public.php`); shared controllers/views use `Support/SurveyCluster` (`name()`, `route()`, `permission()`, `title()`) instead of hard-coded names; scoring in `Support/Riasec.php`. SQLite survey tests (`tests/Feature/Survey`) run with `DB_CONNECTION=sqlite DB_DATABASE=:memory: CMS_DB_DATABASE=:memory:`; that suite rewrites `storage/app/developer/permission-manifest.json` of the machine it runs on, so back the file up first. Details: `docs/survey-module/06-CAREER-ORIENTATION.md`, `docs/CHI-TIET-KIEN-TRUC.md`.
- **Multi-channel publishing (`/cms/truyen-thong`)**: `Services/Social/SocialPublicationService` sends a snapshot of a post (`SocialSnapshotBuilder`) to channels through the interface `SocialChannelAdapter` (validateConnection/publish/remove/syncStatus/syncMetrics); `SocialChannelRegistry` maps a `SocialChannel` to its adapter and `CmsBackendServiceProvider` registers Facebook and Zalo OA ones only when their settings are `configured()` (otherwise the channel answers "not connected" and nothing is sent). New channel = new adapter + registration, never a change to the publication service. Adapters talk server-to-server and must never put a token or secret in a result, message or log. Accounts/history are scoped by `ProjectContext::dataKey()`. Tests: `tests/Feature/Social`. OAuth callback = `/cms/truyen-thong/tai-khoan/facebook/callback` (must match `META_REDIRECT_URI` and the Meta app).
- **Never run the whole `vendor/bin/phpunit` against data you care about**: older tests use `RefreshDatabase` and wipe the database. `phpunit.xml` points at a non-existent database on purpose; run only `tests/Unit/Homepage` (no DB) or pass a dedicated test database.

## Dev/Build per theme (asset profiles)

Theme assets can be built/watched for all themes or for one. This only splits CSS/JS/views; **it does not split database data** (a single-theme build on a shared DB still shows every project's content: deploy each project with its own DB, or scope content with a key such as `project_key`/`site_id`/`theme_key` filtered in every query; never use `NBD`/`BDA` title prefixes as the separation). Full reference and decisions: README.md section 8.

- **Registry**: `scripts/theme-profiles.mjs` is the only place that declares themes for builds: entries (CSS/JS globs), `dependencies`, `fallbackEntries`, `unusedViews`. Themes: `default` (Khuyến nông), `nam-binh-duong`, `ban-de-an`. Sources stay in `Modules/CmsFrontend/resources/assets/{css,js}/screens/<theme>/`; shared assets = everything outside `screens/**`; Core, CmsBackend and the Materialize theme are always built.
- **Dependencies**: `ban-de-an` needs `nam-binh-duong` (its layout loads that theme's `theme.css/js`). `nam-binh-duong` and `ban-de-an` fall back to `default` views `layouts/sections/{styles,scripts}Front`, so they must carry `screens/default/shell.css` and `shell.js` (`fallbackEntries`).
- **Modes** (process env, never `.env`): `CMS_ASSET_MODE=all` (default) or `single` + `CMS_ASSET_THEME=<key>`. Single: only shared + that theme + its dependencies are built/watched; the admin theme selector is locked; the DB option `cms_public_theme` is never modified, and a stored theme without assets falls back to the built theme with a log warning.
- **Runtime**: `Modules/CmsBackend/app/Support/AssetProfile.php` decides the mode in this order: env vars → `public/hot` present (Vite dev, treated as all) → `public/build/theme-build.json` → all. `ScreenTheme::choices()/key()` and `ScreenThemeController` use it. Never leave `public/hot` on production; run `php artisan config:clear` after changing the profile variables.
- **Output** (`public/build` is never written by a build): `build-exports/all-themes/build`, `build-exports/themes/<theme>/build`, and `build-exports/cms/build` (`build:cms`). To deploy, copy the whole content (`manifest.json`, `theme-build.json`, `assets/`) of exactly one profile folder into the target project's `public/build`, back up the running one first, and never mix files of two profiles.
- **Checks**: `theme-build.mjs` fails the build if a `@vite()` used by a theme's views (including `default` fallback views) is not built, if the manifest lacks Core/CmsBackend/CmsFrontend or a profile entry, if a single build contains another theme's entry, or if a referenced file is missing.
- **Deployment matrix**: framework dev and theme-switch demo = `all-themes` + master DB; Nam Bình Dương / Ban Đề án / Khuyến nông = `nam-binh-duong` / `ban-de-an` / `default` + a separate DB for each.
- **Status**: registry, `--check-only` and the four real builds passed on 09/11/2026 (served from a copy of `public/`); Khuyến nông (KNCT) has run a single-theme `build:default` on server 228 since 2026-11-13. Still NOT confirmed: real `dev:*` runs with Ctrl+C. Details: `docs/CHI-TIET-KIEN-TRUC.md`.

## Other conventions

- The Laravel 12 + legacy-controller migration was verified in a real browser on 2026-11-06 (PHP 8.3 and 8.2.27); details in `docs/CHI-TIET-KIEN-TRUC.md`. The two transactional HTTP tests refuse `cms_workspace` unless the opt-in flag above is set.
- **Local dev gotcha**: `php artisan serve` is single-threaded. Saving a Banner whose avatar is an `http://127.0.0.1:8011/media/...` URL makes the server fetch its own URL and deadlock; test that form with a second server on another port (or a multi-worker server).
- **Laravel 12 notes**: `composer.json` pins `config.platform.php = 8.2.99`; `intervention/image` is v3 (no `Image::make`, see `BannerDataProvider`); the custom `url` binding in `AppServiceProvider` must not call `instance('routes')` again (infinite recursion); Jetstream/Fortify were removed (login/logout/password = Breeze-style controllers in `app/Http/Controllers/Auth` + `routes/auth.php`); `route:cache` works but `bootstrap/cache` stays untracked, so run it on a server only as a deliberate deploy step and `route:clear` after route changes. Server deploy know-how (KNCT, NBD on host 228) lives in the Claude memory notes, not in git.
- Autoload (composer.json): `Modules\CmsBackend\` → `Modules/CmsBackend/app/`, `Modules\CmsFrontend\` → `Modules/CmsFrontend/app/`; global helpers in `app/Helpers/GlobalHelpers.php`.
- Content deletion: "Xóa" is soft delete; "Xóa vĩnh viễn kèm tập tin" (admin-only) requires the post to be unpublished first, checks menu/banner/child-post links, and must keep files still referenced by other content (never delete a whole folder by post ID alone).
- Homepage fragment cache is disabled in debug; in production it keys on theme/version/content stamp, and public-visibility rules (approval status, schedule, expiry, internal categories) must be enforced both when querying and when caching.
- Stale per-module `AGENTS.md` files (leftovers of the Khuyến nông source) were removed: `Modules/CmsBackend/AGENTS.md` earlier, `Modules/CmsFrontend/AGENTS.md` on 2026-11-17 (every path it named no longer exists). AI context = this file + `README.md` + `docs/`.
- **Two copies of `AbstractPostController` still run side by side, on purpose.** `Modules/CmsBackend/app/Http/Controllers/Shared/` is the canonical one (translations via `saveTranslations`, `ModuleUrl` route names, `admin.*` language keys) and the Editorial/CDN controllers use it. `app/Http/Controllers/AbstractPostController.php` is the legacy copy; only the old Video and ImageLibrary controllers still extend it (the Banner, Page, Post and LinksWebsite legacy controllers were removed; their `/bai-viet`, `/trang`, `/banner`, `/lien-ket` GET addresses redirect to `/cms/...` through the catch-all in `routes/web.php`). Do not add features to the legacy copy, and do not delete it until Video/ImageLibrary are moved to module controllers and tested; a write screen can change behaviour (it would start writing `post_translations`).
- Views under `resources/views/{pages,_partials}` are NOT all dead: `Modules/CmsBackend/config/screens.php` maps module view names to them and the module controllers (e.g. `Shared/PageController` → `_partials.trang.table-trang`) render them. Inside them always build links with `ModuleUrl::route(...)`, never bare `route('trang.edit')`: the old route names no longer exist.
- The post picker (`x-input-post-select`) opens the module route directly via `ModuleUrl::route`; the toggles `api.update-homepage` / `api.update-commentpage` are served by `Modules/CmsBackend/.../ContentFlagsController` (keep their names/addresses, the admin scripts read them from `window.cmsUrls`). `GuardEditorialLegacyRoutes` is still attached to those two routes.
- The seven older admin screens (users, roles, menus, categories, ads, comments, activity log) are in the sidebar (root `resources/menu/verticalMenu.json` is merged with the project menu) and their controllers now live in `Modules/CmsBackend/app/Http/Controllers/Shared/` (`UserController`, `RoleController`, `MenuController`, `CategoryController` + `AbstractTaxonomyController`, `AdsController` + `AbstractAdsController`, `CommentController`, `ActivityLogController`); the role editor API is `Modules/CmsBackend/.../Api/RoleController` (routes in `routes/api.php`). Moved unchanged (same routes, names, views); only app/Http/Controllers/{File,Language,Profile,Setting,Auth} remain at the root. Create/edit/delete flows were exercised in the browser on 2026-11-09. They stay until the permission manifest of each project is checked or the owner decides; see the memory note `legacy-unlinked-admin-screens`.
- **`CMS_ROUTE_PREFIX` must not be empty.** With an empty prefix the administration overview (`/`) collides with the public home, the route `cms.dashboard` disappears and every signed-in request ends in a 500 (`Route [cms.dashboard] not defined`). Use `cms` (the default). A server `.env` carried `CMS_ROUTE_PREFIX=""` from an older deployment: check it when deploying.
- Production deployments set `CMS_PROJECT_KEY` (`khuyen-nong`, `nam-binh-duong`, `ban-de-an`; `bandean-v2` exists for local/dev and a future server); the permission manifest (`storage/app/developer/permission-manifest.json`) is bound to that key. While the manifest file is absent every permission is available; once it exists only the listed slugs are.
- The Khuyến nông/Sóc Trăng sources are separate; changes here must not be applied back to them or their databases.
